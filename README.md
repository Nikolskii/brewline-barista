# brewline-barista

Интерфейс бариста системы **Brewline** — виртуальной очереди заказов в кофейне.
Бариста видит очередь на своём устройстве и меняет статусы заказов; изменения
синхронно приезжают на табло в зале и клиенту.

Один из контейнеров системы (C4). Соседние репозитории: `brewline-backend`
(API и SSE), `brewline-display` (табло в зале), `brewline-infra` (локальный
docker-compose и деплой), `brewline-docs` (документация, ADR, диаграммы).

## Стек

- React 19 + TypeScript
- Vite
- SCSS Modules
- TanStack Query
- Типы API — из npm-пакета `@brewline/api-types`, генерируемого из контракта backend

## Архитектура frontend

Проект использует **FSD-lite**: достаточную для этого SPA дисциплину слоёв без
полного набора формальных сегментов FSD.

```text
app → pages → widgets → features → entities → shared
```

Верхний слой может зависеть только от себя и слоёв правее. Поэтому экран не
ходит в HTTP напрямую, а карточка заказа не знает, как выполняется действие
бариста.

| Слой       | Ответственность                         | Примеры в проекте                 |
| ---------- | --------------------------------------- | --------------------------------- |
| `app`      | Корневая композиция и провайдеры        | `App`, `QueryClientProvider`      |
| `pages`    | Полноэкранный пользовательский сценарий | `login`                           |
| `widgets`  | Крупные блоки страницы                  | будущая доска очереди             |
| `features` | Законченное действие пользователя       | `auth/sign-in`                    |
| `entities` | Предметная сущность и её модель         | `order`: REST-снапшот и Query-хук |
| `shared`   | Нейтральный код без бизнес-смысла       | HTTP-клиент, конфигурация         |

У каждого слайса есть public API — `index.ts`. Код из другого слайса импортирует
только его, а не внутренние `ui/`, `api/` или `model/`. Не используем общие
технические корневые папки `components/`, `hooks/`, `helpers/` и `api/`: они не
выражают ответственность кода и со временем становятся свалкой.

## Запуск

Нужен работающий backend — интерфейс бариста только отображает и меняет очередь,
данные живут в нём.

**1. Поднять backend и базу** (в соседнем репозитории):

```bash
git clone https://github.com/Nikolskii/brewline-backend.git
cd brewline-backend
docker compose up          # MongoDB + backend на http://localhost:3000
npm run seed               # тестовые заказы в очереди
```

**2. Запустить интерфейс:**

```bash
npm install
cp .env.example .env       # адрес backend
npm run dev                # http://localhost:5174
```

Порт `5174` зафиксирован в `vite.config.ts` (`strictPort`): `5173` занимает табло,
а список разрешённых origin на стороне backend задан явно — уехавший порт означал бы
отказ CORS вместо данных.

Фронт ходит к API **кросс-origin через CORS**, dev-proxy не используется — так дев
повторяет прод (ADR 0004). Адрес задаётся переменной `VITE_API_URL` и обязателен:
без неё приложение падает на старте, а не запрашивает молча само себя. Origin фронта
должен быть в `CORS_ORIGINS` на стороне backend.

Версия Node зафиксирована в `.nvmrc` — она же используется в CI.

## Как ведётся разработка

Задача → ветка → pull request → зелёный CI → merge в `main`. Прямой push в `main`
не используется: CI после факта только сообщает о поломке, а гейтом становится
только тогда, когда блокирует слияние.

Проверки разложены по цене ошибки:

| Событие      | Что происходит                    | Почему так                                                                        |
| ------------ | --------------------------------- | --------------------------------------------------------------------------------- |
| commit       | Prettier на изменённых файлах     | быстро и чинится само; коммит — личный чекпоинт, незавершённый код в нём нормален |
| push в ветку | ничего                            | черновики должны выкладываться свободно                                           |
| pull request | `npm ci` → формат → линт → сборка | код становится общим — здесь единственное место для строгости                     |

Хук на коммит ставится сам при `npm install` (скрипт `prepare`, husky). Обойти его
можно флагом `--no-verify`; именно поэтому те же проверки продублированы в CI.
